Seguridad en APIs REST: Guía Definitiva de Autenticación con JWT, Refresh Tokens y Rate Limiting

Por Sara Domínguez (Ciberseguridad de Software) • 5 de abril de 2026 • Lectura: 9 min
Figura: Arquitectura segura de tokens con corta duración (15 min) y renovación protegida contra XSS y CSRF.

Con la consolidación de las arquitecturas SPA (Single Page Applications) y aplicaciones móviles, las APIs REST son el corazón neurálgico de cualquier servicio moderno. Sin embargo, los errores en la gestión de tokens de sesión son una de las principales puertas de entrada para brechas de datos masivas según el top 10 de OWASP para APIs.

Publicidad

1. El Error Crítico: Guardar JWTs en localStorage

Almacenar tokens de autenticación en el localStorage o sessionStorage del navegador expone la sesión a cualquier script malicioso ejecutado a través de una vulnerabilidad Cross-Site Scripting (XSS). El token de refresco debe guardarse siempre en una cookie con atributos HttpOnly, Secure y SameSite=Strict, la cual es invisible e inaccesible para JavaScript.

2. Estrategia de Doble Token (Access Token + Refresh Token)

  • Access Token (Corta duración: 10-15 minutos): Se transmite en la cabecera Authorization: Bearer <token> para autorizar peticiones rápidas sin consultar la base de datos cada vez.
  • Refresh Token (Larga duración: 7 a 30 días): Almacenado en cookie segura. Permite solicitar un nuevo access token de forma transparente cuando el anterior expira.

3. Rate Limiting: Freno al Brute Force y Denegación de Servicio

Todo endpoint de login y recuperación de contraseña debe limitar las peticiones por dirección IP o usuario (por ejemplo, máximo 5 intentos por minuto) mediante algoritmos de Token Bucket implementados en Redis o en Nginx.
